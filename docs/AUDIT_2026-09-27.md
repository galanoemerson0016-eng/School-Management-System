## 3. Application Architecture

The desktop renderer enters through `app/src/main.tsx` and `app/src/App.tsx`. Authentication gates the application and backup lifecycle. Pages manage learners, enrollment, sections/subjects, attendance, grades, PACE and school forms. Zustand stores coordinate UI state and services. `database.ts` owns IndexedDB, encrypted serialization, migrations, snapshot/restore and the recoverable localStorage settings journal.

Learner LRN is a cross-module identity, referenced by enrollment, class/grading records, observed values, attendance and SF2 maps, SF10 history, and PACE settings. Several datasets remain split across IndexedDB, localStorage and loaded Zustand state. A transaction in one store alone is therefore insufficient for a complete identity change. The new learner service uses one database commit plus the existing durable settings journal; loaded state updates follow successful persistence.

Backups span full JSON snapshots, Excel rescue exports, automatic/incremental scheduling, native paired-file validation and optional Drive synchronization. Export files may contain readable school records. Electron's preload exposes privileged operations to the renderer; the main process now checks the originating window/frame/document before accepting IPC. The LAN gateway is a separate trust boundary with pairing and token checks.

The license portal authenticates an administrator through Firebase. Firestore rules enforce authorization. Purchase requests and payment orders reach Cloud Functions, which call Xendit and issue license records. The payment service now validates callbacks and performs license/order changes in a single transaction. Neither the new rules nor the cloud functions were deployed during this audit.

## 4. Critical Problems

### D01 — Bulk operations and restore can commit partially

- **Confidence / status:** CONFIRMED / VERIFIED.
- **Affected files:** `app/src/services/database.ts`; new `database-audit-regressions.test.ts`.
- **Problem/root cause:** An invalid later IndexedDB request can throw synchronously after earlier requests were queued. Rejecting the surrounding promise does not abort the transaction; an earlier write/delete or restore clear could commit.
- **Impact:** Partially replaced or missing school records despite a reported failure.
- **Fix:** Explicitly abort the active transaction on synchronous request-construction failure for bulk puts, bulk deletes, and restore batches.
- **Testing:** Regression cases reproduced partial put/delete failure before the fix; tests now assert the original dataset survives invalid later operations. An uncloneable restore record also preserves previous data.

### D02 — Legacy learner migration silently collapses duplicate LRNs

- **Confidence / status:** CONFIRMED / VERIFIED.
- **Affected files:** `app/src/services/database.ts`; `database-audit-regressions.test.ts`.
- **Problem/root cause:** Migration from an ID-keyed learner store to an LRN-keyed store used replacement writes without validating LRN uniqueness before deleting the original store.
- **Impact:** Two legacy learners could become one record during upgrade.
- **Fix:** Validate normalized keys and duplicates first; abort invalid migration; use insert semantics so collisions cannot silently replace a row. Schema version remains 13.
- **Testing:** Synthetic legacy duplicate fixture failed before the fix and now preserves the original schema and both learners. Existing migration tests still run.
- **Compatibility/recovery:** Duplicate records require supervised reconciliation, not automatic guessing. Back up a copied profile before upgrade; preserve the old database on failure. See the rollout guide.

### D03 — Learner identity/cascade operations are not atomic

- **Confidence / status:** CONFIRMED / VERIFIED for tested single-process workflows; cross-module concurrency remains D09.
- **Affected files:** `app/src/stores/app-store.ts`, new `app/src/services/learner-record-service.ts`, `app/src/services/database.ts`.
- **Problem/root cause:** Learner edits, reference changes and deletions previously committed independently; some deletes relied on loaded state, omitting historical records. UI could update before durable success.
- **Impact:** Orphaned grades, attendance, enrollment, SF2 and historical identities; silent replacement when adding a duplicate learner.
- **Fix:** Serialize learner operations; reject duplicate/colliding identities; query stored relationships; commit database changes together; journal SF10/PACE changes and copied Grade 1 remarks; update UI after persistence. Preserve permanent local history on deletion.
- **Testing:** Seven integration tests cover identity propagation, SF10/PACE/remarks, collisions, failure rollback, unloaded references, delete failure and duplicate adds. Existing broader CRUD/report/backup tests are retained. In-memory SF10/PACE consumers and concurrent independent editors need the manual checks below.

### S01 — Ordinary authenticated cloud users qualify as administrators

- **Confidence / status:** CONFIRMED in repository rules / FIXED IN SOURCE; deployment verification required.
- **Affected files:** `firestore.rules`, `license-portal/firestore.rules`, `license-portal/src/App.tsx`, new `license-portal/functions/grant-admin.js`.
- **Problem/root cause:** The old administrator predicate accepted non-anonymous providers rather than an explicit privilege assignment.
- **Impact:** An ordinary authenticated identity could receive administrative access if these rules are deployed and such accounts can be obtained. The live project's signup configuration and deployed rules were not inspected.
- **Fix:** Require `admin: true` in trusted custom claims; portal checks the same claim; constrain public purchase creation fields/status; supply a narrowly targeted operator role-grant utility.
- **Testing:** Source review, portal typecheck/build, role-grant syntax check. No emulator or deployed-rule test: source correctness is not proof of live enforcement.
- **Rollout:** Grant verified intended admins before deployment; refresh their token; test negative identities in staging. [Firebase custom-claim guidance](https://firebase.google.com/docs/auth/admin/custom-claims) supports trusted server assignment. Follow [security rollout notes](SECURITY_ROLLOUT_2026-09-27.md).

### D08 — PACE ratings do not distinguish school years

- **Confidence / status:** CONFIRMED key design / DEFERRED; end-to-end rollover needs runtime verification.
- **Affected files:** `app/src/pages/PaceFormPage.tsx` (notably `ratingsStore[selectedLrn]` and localStorage saves), related PACE/SF9 readers and exports.
- **Problem/root cause:** Rating maps use LRN as the only key; school year is a field inside the entry. Returning the existing entry across years and writing under the same key does not retain separate historical ratings.
- **Impact:** Reusing a learner across school years can overwrite or reuse prior-year assessment data. This is a release blocker.
- **Recommended fix:** Introduce a versioned year-plus-LRN data model, preserve all existing raw maps, migrate each entry using its stored year, quarantine missing/ambiguous years for review, and update every reader/export together. Test two years for the same learner, old backups, restore, and LRN rename.
- **Why deferred:** A hurried key substitution would break compatibility and cannot reconstruct already-overwritten history. The audit safely fixed LRN propagation without pretending to solve year separation.

### D10 — SF1 import bypasses the repaired manual learner identity path

- **Confidence / status:** CONFIRMED source path / DEFERRED; failure injection on the import UI remains pending.
- **Affected file:** `app/src/stores/app-store.ts`, `importStudentsFromSF1`.
- **Problem/root cause:** Temporary-LRN matching has its own duplicated cascade that deletes the old learner before independently moving references. It also prepares matches from an initial list while awaiting user conflict resolution. The final repository-wide pass confirmed this path is separate from the repaired manual `updateStudent` path.
- **Impact:** A failed temporary-to-official LRN import can leave the original profile missing and references partly moved. Academic settings are not covered by that duplicate cascade. Repeated identities within an import can use stale matching data.
- **Recommended fix:** Reuse the durable learner service with per-row revision/collision checks after conflict resolution; refresh all loaded consumers after each successful row. Define and report partial-import outcomes explicitly; preserve skipped rows and existing conflict-dialog behavior.
- **Why deferred:** Import intentionally permits interactive merges and row skipping; blindly wrapping the whole workflow in a long-held queue/transaction could deadlock user actions or change import semantics. It needs dedicated import fixtures before removing the duplicate cascade. Manual-edit tests do not certify this import path.

## 8. Security Findings

Confirmed findings are S01–S08 above. Exploitability depends on the relevant boundary: the cloud rules flaw requires the vulnerable rules/account configuration; QR HTML requires malicious interpolated data; CSV formulas require opening exported cells in a spreadsheet; plaintext tokens require file access. These conditions are different from a remotely exploitable desktop compromise and were not conflated.

Source secret scan found `[REDACTED SECRET DETECTED]` in `app/src/services/cloud-sync.ts` and `app/scripts/get-gdrive-refresh-token.cjs`. They contain installed-application OAuth client configuration. A bundled native-app client secret is not a confidential server secret; verify client type, redirect restrictions, scopes and PKCE, and rotate/reconfigure through the owner if appropriate. No secret value belongs in this report. User token files were not inspected. Firebase public client configuration is not itself proof of a leaked server credential.

Hardening still needed: staged rule negative tests, API abuse controls, bounded/minimized diagnostics, review of all export surfaces for formula-like inputs, authenticated LAN/offline reconnection tests, and signed license entitlements. SQL injection is not a directly applicable finding in an IndexedDB/Firestore architecture. No unsupported claim of SQL injection or command execution is made. Existing Electron isolation and gateway pairing are useful controls; new IPC checks add origin/frame ownership.

## 9. Database & Data Integrity Findings

The application uses IndexedDB object-store keys/indexes rather than database-enforced foreign keys. Relationships are the responsibility of application code. D01–D05 close concrete partial-write and identity defects. Full snapshots already use strict data access; strict rescue reads now align with that principle. The existing journal bridges IndexedDB and portable localStorage settings and is replayed before new journal-bearing commits.

Atomicity is bounded: IndexedDB commits do not make every independent UI store, localStorage consumer, browser tab or external file part of one distributed transaction. A settings replay failure may require recovery after the database commit. Raw opaque legacy records must remain preserved for recovery. D07, D08, D09 and H01 remain explicit blockers/limitations, not silently accepted correctness.

There was no live migration or database reset. Schema version stays 13. Duplicate legacy LRNs now halt upgrade instead of destroying records. Existing fixture coverage exercises valid/old/encrypted data and restore paths; it does not prove every historical production variant. Before release, test copied profiles and verify counts, representative grades/attendance, SF10/PACE history and export totals after restart.

## 10. Backup & Restore Findings

**Trust assessment:** Automated fixture coverage and atomic native-file tests support the reviewed paths, but an untested school profile or external Drive restore is not certified. JSON backup and Excel rescue output complement one another; an Excel workbook is not necessarily a complete lossless replacement for every internal setting/history record.

Confirmed repairs: abort invalid restore batches; refuse incomplete rescue export; remove portable SMS credentials; clean up backup scheduling and preserve dirty changes during backup. Native paired backup writes/checksums and retention have three passing tests. Existing files and retention directories were not operated on.

Remaining issues: some future-version acceptance is permissive rather than uniformly fail-closed; preview-database cleanup handles blocked/error conditions without strong assurance; health counts can hide unreadable data. Hashes detect accidental integrity changes but are not digital signatures or encryption. JSON and spreadsheet exports can contain readable personal data, and old backups may include SMS credentials. Preserve them securely rather than rewriting them during this audit.

Release recovery drill: validate file/version/completeness, preserve a separate safety snapshot, restore into a synthetic/copied profile, verify all datasets and settings, restart, then compare reports and counts. Simulate invalid JSON, missing stores, duplicate IDs, unsupported future version, storage quota failure, interrupted journal replay and locked/read-only backup directory. See the rollout guide for compatibility and downgrade details.

## 11. Authentication & Authorization Findings

Local authentication uses salted PBKDF2 (310,000 iterations), a random data-encryption key with AES-GCM wrapping, and native safeStorage recovery where available. Password changes, wrapping and backup recovery must be exercised on copied profiles; license reactivation alone cannot decrypt records. The setup copy now says this accurately.

The desktop is effectively a local owner application. Permissive role helpers (including subject-leader checks) are not a trusted multi-user school authorization boundary. Do not infer secure shared-machine roles from hidden UI actions. A proper multi-user design requires explicit ownership, trusted enforcement and migration, so no superficial role rewrite was attempted.

Cloud authentication now requires a separate administrator claim for privileged portal use and rules access. Intended administrators must receive that claim before deployment. Ordinary authenticated users must be denied in negative tests. Drive credentials migrate to protected storage on the next successful save; older executables cannot read the new envelope and may require reconnecting Drive on rollback. Actual Windows/macOS secure-storage behavior remains a native acceptance test.
