# Release FormEase Pro (Enhanced Workflow v2.3)

Prepare, verify, and publish a new official release for FormEase Pro by strictly following this workflow.

---

## 1. Pre-Flight Verification & Health Check
Before initiating the release, verify project health and data safety:
1. Inspect Git working tree state (`git status`).
   - Verify all feature changes, new services (`grade-reconciliation.ts`, `shs-g12-excel-export.ts`, `database-rescue-export.ts`), and official templates in `app/public/templates/` are accounted for.
   - Stage and commit working tree code if needed (`git commit -m "feat/fix: ..."`).
2. Run pre-flight build check in `app/`:
   ```bash
   npm run build && npm run obfuscate:electron && npm run release:check && npx tsc --noEmit
   ```
3. Run complete automated unit and integration test suite in `app/`:
   ```bash
   npm test -- --run
   ```
   - Verify all test suites pass with **0 failures**, specifically checking:
     - `grade-reconciliation.test.ts` (verifying self-healing, unhiding Elem/JHS subjects, restoring PE & Health)
     - `ecr-excel-export.test.ts` (32 tests covering Academic, EPP/TLE, MAPEH, GMRC, and all SCP programs)
     - `shs-g12-excel-export.test.ts` & `sshs-excel-export.test.ts` (Grade 12 K-12 and SSHS Pilot exports)
     - `sf9-*.test.ts` (SF9 multi-level report cards)
4. If any pre-flight verification step fails, **ABORT immediately** and display the error traceback.

---

## 2. Determine Release Type & Versioning
Determine the version bump level relative to the current release (`v3.3.1`):
- **Patch** (e.g., `3.3.1` -> `3.3.2`): Critical client data self-healing, bug fixes, template adjustments, and formula preservation.
- **Minor** (e.g., `3.3.1` -> `3.4.0`): New Senior High School Grade 12 3-Term ECR, SSHS Pilot ECR, SCP templates (SPFL, SPJ, SPA, SPS, SPTVE, SSES/SPSTEM), and SF9 multi-level exports.
- **Major** (e.g., `3.3.1` -> `4.0.0`): Structural architectural overhauls or breaking database schema migrations.

## 7. CI/CD Workflow, Checksum & Multi-Platform Safeguards
Verify release asset automation integrity:
1. **Metadata Upload List (`.github/workflows/release.yml`)**: Ensure `app/release/*.yml` (`latest.yml`, `latest-mac.yml`) and `app/release/*.blockmap` are included in the release upload files section so Windows and macOS update metadata are published to GitHub Releases.
2. **SHA-512 Hash Generation (`app/scripts/patch-metadata-ci.cjs`)**: Ensure `patch-metadata-ci.cjs` dynamically re-computes `crypto.createHash('sha512')` for renamed binary assets (`FormEase.Pro.Setup.X.Y.Z.exe` / `.dmg`) and saves patched metadata back into `app/release/latest.yml` and `latest-mac.yml` to prevent `404 latest.yml` or `sha512 checksum mismatch` errors.
3. **Google Drive Sync & Old Asset Purge (`app/scripts/sync-gdrive-release.cjs`)**: Automatically deletes previous version installer binaries from the target Google Drive folder and uploads fresh v<new-version> release binaries (strictly the `.exe` for Windows and the 2 `.dmg` files for macOS; excluding `.yml`, `.yaml`, `.zip`, and `.blockmap`).
4. **Seamless 1-Click NSIS Auto-Updater Protection (`app/package.json` & `app/electron/main.cjs`)**: Ensure `"nsis": { "oneClick": true }` in `package.json` and `autoUpdater.quitAndInstall(true, true)` in `main.cjs` so Windows auto-updates perform a silent background binary swap without triggering interactive installer wizard prompts that uninstall the app.

## 8. Create Release Commit & Git Tag
1. Stage all modified and new production files:
   ```bash
   git add app/package.json app/package-lock.json app/src/ app/public/templates/ VERSION_HISTORY.md app/dist-electron/ .gitignore .github/workflows/
   ```
2. Commit with the conventional release message:
   ```bash
   git commit -m "chore(release): v<new-version>"
   ```
3. Create an annotated Git tag matching the exact version:
   ```bash
   git tag -a v<new-version> -m "Release v<new-version>"
   ```
4. *Re-tagging safeguard*: If a release tag ever needs to be updated or re-triggered, explicitly delete local (`git tag -d v<new-version>`) and remote (`git push origin :refs/tags/v<new-version>`) before re-creating.

## Strict Rules
- **Never skip Preview**: Always display the preview and receive confirmation before writing file changes.
- **Fail-Fast**: If `npm run build`, `npm run obfuscate:electron`, `tsc --noEmit`, or `vitest run` fails, stop immediately.
- **Data Protection Guarantee**: Ensure the self-healing reconciliation module is always included in the build to safeguard existing client databases.
- **Reverse Chronological**: Ensure latest releases are at the top of `VERSION_HISTORY.md`.
- **Tag Formatting**: Always prefix version tags with `v` (e.g., `v3.4.0`).
- **Refspec Precision**: Always use `refs/heads/main` when pushing to avoid refspec ambiguity.
- **Dynamic Checksum Protection**: Always write patched `latest.yml` and `latest-mac.yml` with re-calculated SHA-512 hashes back to release metadata before uploading assets.
- **Safety & Confidentiality**: Never mention repository visibility toggling (public/private switching) in user-facing release notes (`VERSION_HISTORY.md` or `SettingsPage.tsx`).
- **Private Repository Restoration**: Always ensure repository is switched back to `private` after release pipeline completes.
